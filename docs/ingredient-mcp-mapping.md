# 食材与麦当劳 MCP 餐品匹配方案

研究日期：2026-10-24。14 种真实餐品、对应 3D 模型、按食材匹配与后台自动选店均已接入游戏。

## 查询依据与适用范围

通过本项目配置的真实 MCP，执行 `tools/list`、`query-nearby-stores`、`query-meals`、`query-meal-detail`、`calculate-price`。未调用 `create-order`。

为研究使用上海人民广场附近的两个样本门店，不代表玩家所在地。按用户要求，游戏后台默认也在这一区域自动选择营业门店，不展示门店界面：

| 麦当劳上海食品一店餐厅 | `1450056` | 对照菜单及门店差异 |

14 个候选款式的算价均返回 `code=200`。这验证了样本门店在查询时接受相应商品和选配结构，不代表已验证真实创建订单或所有门店均可售。菜单、价格、特调和可用取餐方式需在后台选定的营业门店重新获取。

精简查询记录见 [mcd-menu-2026-10-24.json](research/mcd-menu-2026-10-24.json)。记录不含 Token 和个人账户信息。

## 功能目标

用真实门店菜单作为候选池，由确定性的游戏规则选出最接近玩家食材的真实商品。料理名称、模型类型、菜谱收集记录和后续下单商品应来自同一份匹配结果。

现有食材共 11 种：芝麻面包、厚切牛肉、酥嫩鸡肉、鲜香鱼排、金色芝士、翠叶生菜、红熟番茄、酸脆黄瓜、火焰辣酱、烤味酱、金脆薯条；每锅最多 5 份，允许重复。

以下是游戏匹配规则，不是麦当劳官方制作配方。保留主肉类和关键风味；面包、标准酱汁及少量默认配料可以由营地补足。重复肉类优先指向双层款式，不表示 MCP 支持任意增加肉饼。

## 匹配规则与边界

1. **先识别主肉类。** 牛肉、鱼肉、鸡肉形成三个候选集合。只有一种肉类时必须保留该类型；无可售同类商品时告知暂无匹配，不跨类型替换。
2. **混合肉类按数量选择主料。** 数量并列时以最后加入的肉类为主；结果解释主料选择和近似匹配，不虚构官方没有的牛鱼混合汉堡。其他肉类只记录为本锅投入，不宣称都包含在真实商品中。
3. **再区分款式。** 牛肉组优先依次检查：双牛肉加生菜的巨无霸、双牛肉加芝士的双层吉士、芝士加番茄的安格斯、普通吉士、基础汉堡。鱼肉按数量区分单层、双层。鸡肉有面包时按辣味、烤味酱、普通款区分；无面包时按辣味区分鸡翅与麦乐鸡。牛肉与鱼肉缺少面包时可由营地补足面包。
4. **小食独立处理。** 没有肉类时，薯条优先对应薯条；纯芝士只有在实际菜单列出芝士条时才有对应结果。
5. **缺少主料时给出明确提示。** 只有面包、生菜、番茄、黄瓜、辣酱的组合提示补充牛肉、鸡肉、鱼肉或薯条。当前样本没有可据以承诺的纯素汉堡；不把蔬菜组合命名成虚构的官方素食堡。
6. **同类回退。** 双层鱼堡缺货时可回退到麦香鱼；巨无霸缺货时可推荐仍可售的牛肉堡，并在结果中说明换成了哪款。辣味款缺货时，普通同类商品仅作为明确标注「当前无辣味款」的候选，不宣称仍然匹配了辣味。
7. **额外配料只影响相似度。** 投入黄瓜不代表某个无黄瓜特调项的商品就能添加黄瓜；番茄片也不等同于番茄酱。匹配解释可以说明近似之处。

固定判定顺序与清晰的近似提示，让相同食材和相同门店菜单得到相同结果。门店菜单变化可影响实际结果，并在结果中展示实际名称。

## MCP 接入流程

1. 玩家直接选择食材并开始烹饪。后台默认搜索上海人民广场，跳过未营业或营业状态未知的门店，自动选用一家可用门店；查询或匹配失败会尝试其他营业门店，最多三家。界面不显示门店入口、选择弹窗或门店信息。可通过服务端 MCD_STORE_CITY、MCD_STORE_KEYWORD 更改搜索区域。搜索结果缓存 10 分钟，并合并并发搜索；每份生成结果携带该次实际门店供后续报价沿用。
2. 服务端调用 `query-meals`，按门店缓存短时间的候选池。保留分类中上架商品、父商品及其选配关系，避免将仅存在于底层商品字典中的商品误认为可单独点购。
3. 玩家开始烹饪时，服务端接收食材列表，校验 1–5 份有效食材，再按上述规则匹配候选；动画期间获取并校验所选商品详情。
4. `query-meal-detail` 确定实际商品名、图片、默认配料、`rounds` 与 `supportModify`。返回可特调商品时结果可标注「可特调」。默认采用标准配方；特调功能以后按该商品返回的允许选项实现。
5. 返回统一的匹配结果：`recipeId`、`productName`、`storeCode`、`productCode`、所选子项、`modelVariant`、投入食材、匹配说明、查询时间。服务器保存可信商品选择，前端不自行拼装下单参数。
6. 出锅结果同时使用真实餐品名与对应 3D 模型。牛肉堡、鸡肉堡、鱼堡在肉饼形状、层数、面包、芝士和蔬菜上区分；麦乐鸡、鸡翅、薯条使用独立模型。
7. 玩家进入下单流程后重新核对菜单及 `calculate-price`；确认价格、款式和取餐方式之后才调用现有 `create-order`。生成料理本身不创建真实订单。

MCP 网络暂不可用时明确显示查询状态，允许重试查询；不得悄悄将演示菜品标成真实菜单匹配。已有游戏演示模式可继续作为清楚标注的独立模式。

## 实现与验收

- `src/game/data.ts` 定义 14 个菜谱和确定性食材规则；`server/cooking.ts` 从实时可售菜单中匹配同类商品，按接近程度回退。
- `server/automatic-menu.ts` 负责自动选择营业门店；`POST /api/cooking-match` 只需传入 `ingredients`，游戏不需要位置输入。
- `server/mcp.ts`、`server/mcd-data.ts` 验证父商品和子选配关系，支持汉堡包、吉士汉堡包及双层鱼堡，保留标准特调；算价和创建订单沿用同一份可信配置。
- `src/scene/MenuFoodModels.tsx` 与 `BigMacModel.tsx` 生成可交互的 3D 模型，按实际 `modelVariant` 出锅；汉堡层数、鱼排、鸡排、烤痕、5 块麦乐鸡、2 块鸡翅、薯条盒与拉丝芝士条分别建模。
- `src/game/store.ts` 等待真实匹配再揭晓料理，网络失败或取消完整归还食材；旧存档保留背包和巨无霸发现次数，新菜谱独立记录。
- 2026-10-24 通过真实模式的无门店参数接口验证全部 14 款匹配与算价，名称、模型标识、报价商品及门店一致；未创建真实订单。自动测试另覆盖自动选店、菜单重试、缓存、无主料、食材返还、异步揭晓和父子选配。

## 验收重点

- 单一牛肉、鸡肉、鱼肉组合分别生成同类型真实餐品；各规则优先级和双份数量可验证。
- 相同输入在相同菜单下结果一致；混合肉类、纯配料、门店缺货的行为明确。
- 汉堡包、吉士汉堡包、双层鱼堡携带正确父子选配，算价与创建订单使用同一份受信选择。
- 名称、模型、菜谱与报价商品一致，实时查询失败时没有伪造成功结果。
- 料理生成过程中没有创建真实订单；订单仅在原有确认流程中创建。
